## 1. Vision

**A technical society must be an ecosystem, not just an event organizer.**

Most student societies optimize for events: a workshop in August, a hackathon in October, silence in between. L.O.O.M. optimizes for something different — **continuous learning, public contribution, and generational mentorship.**

We exist to build a lasting technical culture on campus that:

- Welcomes absolute beginners without prerequisites or gatekeeping.
- Provides structured, year-round pathways from first line of code to first merged pull request.
- Replaces certificate-chasing with verifiable, portable proof of work.
- Ensures every member who learns eventually teaches the next intake.

> L.O.O.M. exists not to conduct events, but to build a lasting, sustainable technical culture that outlives its founders.

---

## 2. Mission Statement

> **Creating a collaborative technical learning environment where students can learn, build, and grow regardless of prior experience.**

Four commitments define how we work:

- **Beginner-friendly.** Every onboarding path assumes zero prior skill.
- **Inclusive.** Background, branch, year, and prior exposure do not determine access.
- **Collaborative.** Cross-domain teams over isolated silos.
- **Contribution-driven.** Learning is validated by shipping, sharing, and mentoring — not by attendance alone.

## 4. Why L.O.O.M. Exists

### The problem: fragmented resources, structured nowhere

On most campuses, motivated students face the same barriers:

- Beginners feel hesitant or excluded from technical spaces.
- Resources are fragmented — random playlists, disconnected seniors, no guided roadmap.
- Engagement collapses after recruitment, sustained only by one-off events.
- Success is measured by certificates held, not work shipped.

### The L.O.O.M. response

| Dimension | The Traditional Society Model | The L.O.O.M. Ecosystem |
|-----------|-------------------------------|------------------------|
| **Accessibility** | Beginners feel hesitant or excluded. | Strictly beginner-friendly participation and onboarding. No prerequisites. |
| **Guidance** | Fragmented resources without a guided roadmap. | Structured beginner-level guidance with peer-to-peer mentorship. |
| **Engagement** | Post-recruitment drop-off; focused on one-off events. | Consistent, year-round engagement through habits and hands-on projects. |
| **Output** | Certificate-oriented and siloed. | A platform for open-source contribution, hackathons, and collaboration. |

**Our operating principles:**

1. **Zero-Barrier Entry:** Prior experience is never a prerequisite for participation.
2. **Continuous Ecosystem:** We move past the limitations of an event-organizing or certificate-factory model.
3. **Action-Oriented:** The focus is entirely on learning, building, and growing together.

## 5. The Four Pillars

Four interconnected pillars drive a single community engine.

### 5.1 Learning — Fundamentals

Structured foundations before specialization. Curated tracks, beginner workshops, weekly problem-solving practice, and clear milestones so a newcomer always knows the next step.

### 5.2 Opportunity — Exposure

Access to mini-projects, showcases, tech talks, contests, and industry interaction. Learning unlocks opportunity — members apply fundamentals in visible, real settings.

### 5.3 Open Source — Public Collaboration

Contributing beyond the classroom. Curated beginner-friendly repositories, guided first pull requests, and public portfolios. Exposure drives contribution, and open source creates public accountability.

### 5.4 Mentorship — Growth

Seniors help juniors grow and eventually become mentors themselves. Mentorship loops back to fuel continuous learning — closing the flywheel.

**The flywheel in one line:**

> Learning unlocks Opportunity → Exposure drives Contribution → Open Source creates Accountability → Mentorship fuels Learning.

No pillar stands alone. A workshop without a project to apply it fades. A project without a mentor stalls. A contribution without public review does not compound. L.O.O.M. deliberately connects all four.

## 6. Member Journey

**The student journey is a self-sustaining cycle of mastery.**

A typical path through L.O.O.M.:

1. **Beginner** — Join with no prerequisites. Attend onboarding workshops.
2. **Learn** — Follow a track, complete fundamentals, establish a practice habit.
3. **Practice** — Weekly DSA and problem-solving, code reviews, mentor feedback.
4. **Build** — Ship mini-projects, showcase work, collaborate in teams.
5. **Collaborate** — Cross-domain builds, hackathons, joint competitions.
6. **Mentor Others** — Guide the next intake through the same path you walked.

### The generational cycle

> The ultimate goal of a member is to become a mentor for the next intake.

This is what makes L.O.O.M. self-sustaining. Each generation produces the teachers for the next. Knowledge does not leave when seniors graduate — it is transferred, documented, and compounded.

**Progression:** `Beginner → Learner → Builder → Collaborator → Mentor`

## 7. What We Do Year-Round

Vision translated into consistent, year-round engagement. All activity orbits the **L.O.O.M. Core** — the shared standards, mentorship culture, and open-source practice that keep every program aligned.

| Program | Purpose | Cadence |
|---------|---------|---------|
| **Beginner Workshops** | Onboarding. Zero-to-one foundations in code, tools, and community norms. | Start of each intake / semester |
| **Weekly DSA and Problem-Solving** | Habit-building. Sustained, documented practice with peer accountability. | Weekly |
| **Mini-Projects and Showcases** | Applied learning. Ship small, demo publicly, receive structured feedback. | Monthly / rolling |
| **Tech Talks** | Industry exposure. Practitioners, alumni, and maintainers on real-world practice. | Monthly |
| **Peer-to-Peer Mentorship** | Continuous support. Paired and group mentoring embedded in every track. | Ongoing |
| **Hackathons and Open-Source Sprints** | External contribution. Compete, collaborate, and merge code into live projects. | Quarterly / per season |

We deliberately avoid one-off, attendance-only programming. Every activity must connect to learning, building, or mentoring — and produce visible output.

## 8. How We Are Organized

**Cross-department collaboration over isolated silos.**

Departments are not isolated teams; they are parts of one larger ecosystem, centered on **the student.**

### Technical domains

- AI/ML
- Web Development
- Cybersecurity
- DSA and Problem-Solving
- Blockchain

### Enabling functions

- Design
- Sponsorship and Partnerships
- Public Relations and Community
- EVM / Operations (events, venues, logistics)

### Collaboration by default

- **Design + Web Development** build and maintain the community platform together.
- **DSA + Cybersecurity** host joint competitions combining algorithms and security thinking.
- **AI/ML + any domain** pair for applied mini-projects and showcases.
- No member belongs to only one room. Cross-functional teams are the norm for hackathons, sprints, and showcases.

Leadership exists to unblock, coordinate, and mentor — not to gatekeep. Role descriptions, decision rights, and handover notes are documented so chapters survive leadership transitions.

## 9. Open Source and Building in Public

**Breaking out of the classroom to contribute globally.**

We shift the metric of success from *holding internal certificates* to *merging code into real-world, global projects.*

What this means in practice:

- Classroom and closed projects are starting points, not destinations.
- Members progress from passive consumers of knowledge to active builders and public collaborators.
- Curated repositories lower the barrier to a first contribution.
- Pull requests, reviews, and maintainer feedback are treated as core learning — not extracurricular.
- Portfolios are public, verifiable, and portable across chapters and employers.

Open by default applies to the community itself: shared playbooks, open knowledge bases, and this codebase welcome scrutiny and improvement.

## 10. How We Measure Success

We measure success through tangible student outcomes — not headcount at events.

| Outcome | What We Track |
|---------|---------------|
| **Accessibility** | Measurable increase in participation among absolute beginners in technical activities. |
| **Readiness** | Improved placement and internship outcomes through sustained, documented practice and project portfolios. |
| **Excellence** | Consistent participation and victories in external competitions and hackathons. |
| **Network** | Establishment of a robust, active alumni and industry network that feeds back into the community. |

If beginners are not joining, staying, shipping, and eventually mentoring — we are not succeeding, regardless of event attendance.

## 12. Get Involved

### Who can join

Anyone willing to learn and contribute respectfully. There are no skill prerequisites, no branch restrictions, and no year cutoffs.

You are a good fit if you:

- Are new to technology and want structured guidance.
- Can already build and want collaborators, feedback, and real users.
- Want to mentor, review code, organize, design, document, or connect people.

### How to start

1. **Say hello.** Open an [issue](https://github.com/l-oo-m/LOOM/issues) or join the community channel and introduce yourself — what you want to learn, build, or teach.
2. **Pick one track.** Start with a single Beginner Workshop or weekly practice session. Finish one milestone before adding a second.
3. **Ship something small.** A mini-project, a documentation fix, a first pull request. Public and reviewed beats perfect and private.
4. **Ask for a mentor.** You will be paired or directed to group mentoring. No one is expected to figure it out alone.
5. **Give back.** Review a peer, answer a question, improve a guide. Mentorship begins long before a title does.

## 13. Chapters and Federation

Colleges participate as **federation members, not isolated tenants.** Chapters share roadmaps, resources, mentor pools, and playbooks — and compete and collaborate in good faith.

To start or onboard a chapter:

- Publish a chapter profile with leads, tracks offered, and meeting cadence.
- Adopt the core programs in [Section 7](#7-what-we-do-year-round) before adding local variations.
- Connect to the federation network for cross-campus showcases, joint hackathons, and standings.
- Document what works. Chapters are expected to contribute improvements back to the shared playbook.

## 14. Contributing

**We especially welcome first-time contributors.** L.O.O.M. uses its own open-source portal to onboard: good first issues, claimable work, and recognition for merged contributions.

### How to contribute

1. **Fork** the repository and clone your fork.
2. **Find an issue** labeled `good first issue`, or open one describing what you want to improve.
3. **Create a branch:** `git checkout -b feat/your-thing` (or `fix/...`, `docs/...`).
4. **Follow the house rules:**
   - JavaScript/JSX only in source; no TypeScript in application code.
   - Reuse existing components, helpers, and conventions (`components/ui.jsx`, `lib/auth-server.js`, `lib/api.js`).
   - Server-side tenant scoping on every query — never trust `tenant_id` from the client.
   - Keep diffs small and focused. No unrelated refactors.
   - Add or update tests when you add logic (`tests/`, vitest).
5. **Verify:** `npm run lint && npm run test && npm run build`.
6. **Open a pull request** against `main` with a clear description, screenshots for UI changes, and notes on what you verified.

### Areas that regularly need help

- Curated learning resources across the five technical tracks.
- Chapter onboarding playbooks and documentation.
- Accessibility improvements on any page.
- End-to-end test coverage for community and events flows.
- Storytelling and design for chapter outreach.

### Contributor ladder

`First PR merged` → `Triple Merge` → `OSS Regular` → `Code Reviewer`

Reviewers who guide newcomers receive explicit recognition in release notes. Teaching is a first-class contribution.

## 15. Community Standards

Our code of conduct is simple and enforced:

1. **Be kind.** Assume good intent. Offer feedback that helps the work improve.
2. **Be honest.** Never invent activity, metrics, or credentials. Represent sample data as sample. Give credit accurately.
3. **Prioritize beginners.** Impatience with newcomers is the only unwelcome contribution. Every interaction should leave a beginner more capable, not smaller.
4. **Build in the open.** Prefer public discussion, documented decisions, and reviewable work.
5. **Respect people and privacy.** No harassment, discrimination, or sharing of private information. Violations are addressed promptly by maintainers.

Report concerns through [Issues](https://github.com/l-oo-m/LOOM/issues) or directly to a maintainer. Silence that protects harm is not neutrality.

## 16. Platform Overview (For Contributors)

L.O.O.M. maintains a companion platform that turns everyday learning into verifiable proof — roadmaps, resources, projects, open-source tracking, contests and events, mentorship, credentials, insights, forums, and chapter federation.

**Stack:** Next.js 15 · Supabase (Auth + Postgres) · Drizzle ORM · Tailwind CSS · React Flow · GitHub Webhooks · Playwright

**Quick start:**

```bash
git clone https://github.com/l-oo-m/LOOM.git
cd LOOM
npm install

# point at your Supabase project
cp .env.example .env.local   # then fill in your keys

npm run db:migrate            # tracked SQL migrations
npm run db:seed               # roadmaps + resources
node load/seed-community.js   # curated OSS repos (live GitHub data)

npm run dev                   # → http://localhost:3000
```

Open `/setup` to claim the first admin, and schedule the nightly rollups (`load/rollup-federation.js`, `load/rollup-analytics.js`). Full operator documentation is maintained under `docs/`.

The platform supports the community — it does not replace it. Process and people come first; tooling follows.
